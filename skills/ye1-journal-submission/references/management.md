# 多篇文章管理与总览

客户希望统一管理多篇文章、查看投稿进度，或已有总览需要继续维护时，使用客户 Agent 现有的文件、文档及可用浏览器能力。交付三层信息：聊天中的简明总览、客户私人目录中的可编辑总览表，以及每篇文章的材料和投稿记录。这里只规定工作结果，不提供程序、固定界面或后台服务。

## 建立与复用

先复用用户给出的文章清单、已授权读取的材料、投稿回执、历史表格或投稿系统里可见的记录，确认本次纳入哪些文章；已知的信息不让客户重填。已有总览就更新原表，避免反复新建；资料不足时先接入能识别的文章，集中询问确需补充的稿件或入口。不要扫描无关目录或声称已纳入未核实的全部文章；未开启[可选邮件接收](mail-optional.md)时不访问邮箱。检查和整理历史材料不等于授权登录、上传、提交或开启定时监控。

客户指定位置或格式时沿用；否则在合适的私人工作目录建立普通可编辑表格或 Markdown 总览，并告诉客户路径。宿主能可靠创建、更新表格文件时可用 Excel；缺少能力时用可读的 Markdown 或普通表格，不要求客户安装新软件。页面展示、表格格式和文件名可按客户习惯调整。

## 文章、投稿与版本

总览以**文章**为单位，每篇通常一行；一篇文章可关联多次投稿/改投，同一次投稿可有多轮修回。为每篇使用能长期区分的本地名称或标识，并分别记录该次投稿的期刊、稿件号/入口、账号标识、提交日期、状态、版本文件夹及来源；已有标识优先沿用。标题、期刊或作者变动不应自动变成新文章；不同文章即使标题相似也不自动合并。客户无需学习编号规则。

在每篇的私人目录内衔接现有资料，按[逐次投稿留档](submission-snapshots.md)分别保留每次投稿和修回已有的实际材料、作者快照、状态历史及依据；资料缺失时标明，不为只查询状态索取无关信息。改投建立新一轮记录，保留原期刊的结果和原始版本；继续已有草稿不重复建稿。若来源不足以判断是不是同一篇或哪次是当前投稿，保留原记录并标为待核对，不凭标题或日期擅自合并。若有多次仍在处理或状态不明的记录，将各自情况展示，先核对而不凭最新日期选一个当作唯一当前投稿。

## 给客户看的总览

默认展示：文章名称、当前期刊及投稿/本地准备进展、下一步或待处理事项、可核实的截止日期、最后一次**成功查询**的时间。期刊状态保留平台原文，可附简短中文说明；本地准备、草稿和平台状态须区分。缺少期刊、日期或待办时标为未知、待确认或暂未查询，不把未知写成“无”。

同时记录最近一次查询是否成功：本次失败时显示失败或需登录、实际失败时间、上次可信状态及其成功查询时间；从未成功则标为未知。平台给出的状态发生时间与 Agent 发现/查询时间分开。客户可按文章、期刊、待处理事项或状态查看，尽量提供可打开的详情链接或可复制的本地路径；聊天回复优先呈现变化和需处理事项，用户要求看全部时展示完整总览。

用户查看监控安排或总览涉及定时监控时，另展示可核实的任务启用情况、各篇是否纳入、最近实际运行结果和可核实的下次计划；任务启用不等于最近运行成功。可见的审稿详情、编辑决定及待办按[进展与下一步](monitoring-details.md)记录，截止提醒和运行状态按[监控安排](monitoring-schedule.md)处理；未设置或无法核实的内容如实说明。

总览是文章记录的摘要和入口，详情及状态历史保留在对应文章/投稿记录中。一次准备、提交或查询有明确结果后，更新对应详细记录和已有总览；只改有证据的字段并回读对照，保留历史与其他文章。无法确定归属或写入失败时标明缺口，不编造同步成功。仅在客户要求多篇管理或已有总览时建立/维护总览；只处理单篇的任务不强制创建全局表格。

## 与状态监控衔接

对客户指定的已有投稿，按[状态监控](monitoring.md)逐篇只读核对账号、期刊及稿件身份，比较上次可信状态，写入该次投稿历史，再更新总览。多账号或期刊各自核对；一篇登录失效或查询失败不影响其他能查的文章。平台只显示历史片段时记录所见，不补造遗漏事件。材料已保存、已提交和已接收是不同阶段；改投后不要把原刊状态当成新刊状态。

客户要求定时监控时，使用宿主现有调度能力；未获得该要求时只完成已请求的整理或查询。定时任务要能访问同一份私人记录和对应会话，增减稿件及暂停/恢复后核对任务范围；完成一次查询、创建任务和任务真正运行分别报告。无变化且正常时静默保存；实质变化、新故障或明确需要处理的事项按客户约定通知，不自动联系期刊或替客户提交。不存在的截止日、通知渠道及结果不自行补造。
